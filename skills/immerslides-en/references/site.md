# Turn the deck into a scrolling site

Keep the same deck, content order, and design, so readers can scroll through it at `/site`.

## Entry points

The starter and a project generated by the CLI provide three entry points.

- `/` shows the site or the presentation, based on `defaultView` in `src/config.ts`.
- `/slides` always shows the presentation.
- `/site` always shows the site.

To choose the home-page format, edit `src/config.ts` in the generated project. In the package repository, the matching file is `starter/src/config.ts`.

```ts
export const defaultView: 'slides' | 'site' = 'site';
```

The starter defaults to `'slides'`, so `/` opens the presentation, and existing `/#/slug` presentation links keep working. Change it to `'site'` only when the site should be the home page.

Keep `index.html`, `slides/index.html`, `site/index.html`, and Vite's three build inputs. They let a static host open each subpage directly. Deploy the complete build directory.

## Adding a reading page to an existing React site

Render `Site` on the host project's `/site` route, and pass in the existing deck.

```tsx
import { Site } from 'immerslides/site';
import 'immerslides/styles.css';
import { deck } from './deck';

export function ReadingPage() {
  return <Site deck={deck} presentationHref="/slides" locale="en" />;
}
```

`presentationHref` points to the host project's presentation entry. If the site is deployed in a subdirectory, use the URL that includes that subdirectory. `Site` does not register any host routes itself. `locale` sets the language of the site's interface and content. See the "Multiple languages" section of [authoring.md](authoring.md).

Site-specific CSS classes use `immersite` and `immersite-*`. Shared content components keep their existing classes. Styles are provided together by `immerslides/styles.css`.

## Driving the original animation with scrolling

The site uses the existing `RenderSlide`. The scroll position determines the `step`, and content entering or leaving the viewport updates `active`. Keep using `still` and `reducedMotion` to control animation; do not fix them to a static state in the site version. Code focus, flow nodes, connectors, and step-by-step reveals keep working through their existing controlled components.

When a page should stay fixed while scrolling advances its steps, use `SiteStory`. `steps` takes the existing array of titles and descriptions, and `step` takes the renderer's current step. `children` holds the existing chart or code component.

```tsx
import { SiteStory } from 'immerslides/site';
import { CodeBlock } from 'immerslides/code-block';

<SiteStory steps={codeSteps} step={step}>
  <CodeBlock
    filename="register.ts"
    language="ts"
    steps={codeSteps}
    step={step}
    still={still}
  >
    {registrationCode}
  </CodeBlock>
</SiteStory>;
```

In animated mode, the information for the current step is shown at once. A short scroll distance advances to the next step, and scrolling up returns to the previous one. If the content is too tall, the text shrinks first, down to a readable minimum. Only when it still cannot fit the window does the page switch to natural flow. After a step completes, the content carries upward into the next section as you scroll, and scrolling up plays the transition in reverse. The transition range is measured from the bottom edge of the browser viewport. Content before and after stays continuously visible, and shared elements such as the chapter rail stay fixed. When scrolling stops, the view snaps to the nearest complete page. When the system has reduced motion enabled, the fixed, shrinking, and snapping effects are removed, and the full static explanation is shown.

## Steps under reduced motion

When reduced motion is enabled, each page shows its final step in full, and every section of a step-by-step reveal is visible. `SiteStory` also lists the titles and descriptions of all steps, and hides the descriptions that the child component would normally show for only one step. Scrolling no longer advances steps.

Do not copy the code, the step data, or the chapter list separately. The starter's code, flow, and composition examples all reuse the presentation's step arrays.

Pass the props you receive into `SlideFrame`, and wire up the chapter-click action as well. The chapter rail, title, and footer keep their shared rendering, and the site's outer container handles the fixed layout, responsive layout, and transitions. A custom chart with a fixed width and height must supply its own narrow-screen styles. An embedded `SlidePreview` still renders as a static thumbnail.

Shared renderers should use the `actions` from their props, not `usePlayback()`. The site does not mount the playback Provider, control bar, overlays, or speaker notes. `actions.jump(id)` scrolls to the matching section, and the previous and next actions scroll to the adjacent section.

## Linking to a site section

Use `getSiteHref` to build an anchor inside the site.

```tsx
import { getSiteHref } from 'immerslides/site';

<a href={getSiteHref(deck, 'pipeline')}>Read the flow</a>;
```

Use this link in the site, and use `getSlideHref` in the presentation. Give sections you share long-term a stable slide slug.

## Verifying the reading experience

Run the project's type check and build. Open `/`, `/slides`, and `/site`, and confirm that the default format and the fixed entry points are all correct. After changing the setting, check the home page again.

Check the chapter links, opening a section directly, reloading, and browser back and forward. At desktop and phone widths, confirm that text, flows, and code are fully readable. Code may scroll horizontally inside its own area, but the whole page must not overflow horizontally.

While scrolling, check that the page stays fixed, that code lines are focused, that flow nodes and connectors are correct, that the cover's depth effect works, and that the body text carries upward into the next section. Confirm that the transition never shows a blank screen and that the same element does not scroll along with the content. Stop partway through a transition, and confirm the view snaps to a complete page; then scroll again and confirm you can continue. Each page should show only the current information, and advancing a step should not require a long scroll. Click a chapter in the side rail, and confirm it jumps to that chapter. Scroll up, and confirm that steps and transitions can move in reverse. Confirm that looping animations that leave the viewport stop.

Turn on the system's reduced-motion setting, and confirm that the animations, fixed layout, and snapping stop while the content stays readable. Keep native scrolling. Snap only after the user stops partway through a transition, and do not intercept the wheel or lengthen the scroll distance for steps.
